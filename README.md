# weifan · 架构喂饭模式 (Architecture Spoon-feed Coach)

[English](README.en.md) | **简体中文**

现在的常态是：项目让 Agent 快速搭建，大多数时候不做 review——这没问题。但总有一些时刻，你想对项目架构有一点掌控力，或者对 Agent 的做法产生了质疑、想拿到更多实施层面的事实。这时候自己去读代码几乎不可行（Agent 产出的量级摆在那里），直接问 Agent"这块的架构路线是怎样的"效果也很差——它把问的那一句答了，你脑子里还是空的。这个 skill 就是为这些时刻做的。

喂饭（wèifàn）是中文网络用语"喂饭级教程"的缩写——把知识一口一口喂到你嘴边。这个 skill 把它做成了一套可执行的架构教学法：**不逐题回答，而是把你的每个疑问当成认知体系上的缺口，找到缺失的基石，按依赖顺序补——产出不是讲解，是你脑中一座能预测系统行为的模型。**

## 它解决什么问题

4 个高频痛点——全部来自作者真实使用 AI 开发时踩过的坑（语料与方法见 [EVALUATION.md](EVALUATION.md)），不是想象的场景。尤其在你接手一个陌生代码库、或让 Agent 快速搭出来一个项目之后想搞懂它的时候：

**1 · 问得零散，答得更零散——脑子里还是没有俯视图。**
你看到的只是表面，问出的是表面问题，得到的也是孤立的答案。这个 skill 把每个疑问当成认知体系上的缺口：先归约你的问题共同指向哪块缺失的前置，把回答**拔高到架构层**，一轮补一块基石——产出不是几段零散的答案，是一座**能预测系统行为的模型**。每块讲完，用"推一个你没见过的情形"当场验收模型立没立住。

**2 · 项目or行业黑话裸用，全靠你自己停下来问。**
放任agent完成写spec、plan、实施之后，文档和代码注释里通常堆积了很多mock、断言器、槽文件这类行业术语或者项目自造词，在追问阶段会被agent当常识直接使用。skill 的术语准入：任何名词第一次承担论证作用时，必须"**已被你确认 / 当场定义 / 显式占位**"三者取一；配一条可操作判据——把词丢给任意通用网页 AI，它给不出与本仓一致的定义，就不许当已知词用。

**3 · 一次问三个问题，它一口气甩三章节；新知识完全不搭你已知的骨架。**
不控制输出负荷的 Agent，问题多长答案就多长。这里**一轮只推进一个认知中心**：多问先归约成共同缺口，归约不出再排队逐个讲；**每个新块显式挂到已确认的认知上**（继续 / 放大 / 补对端），你说"接不上"时按断点类型对症补桥，不整段重讲。

**4 · 让它"说人话"，它开始讲工地。**
你不懂的本来就是复杂机制；再搬一套同样复杂的现实场景来类比（包工头、施工队、临时工、安全员……），是在原有负担上再压一层陌生实体——你对那个领域可能也只认识两三个。skill 默认直陈：数据结构、数据流、真实名词；比喻只允许"外号＝真名"的一句话命名式，角色演戏的场景比喻一律禁止；读者会编程时优先用代码形态类比（循环、缓冲区、录制/重放）。



## 适用 / 不适用

- ✅ 用户说"带我过一遍架构""这块我从没搞懂过""刚干完活，讲讲现在长什么样了"
- ✅ 四种入口：问题驱动 / 主动游览 / 变更复盘 / 粘贴旧材料的复盘对照
- ❌ 普通架构提问——照常快问快答，**仅显式要求时进入**（说"喂饭"/"weifan"/"spoon-feed mode"）

## 安装

**一行安装**（需 Node；零依赖，只做本机文件复制）：

```bash
npx github:ban-boi/weifan-skill
```

安装器自动检测本机的 Claude Code / Cursor / ZCode 等客户端，把技能装进各自的**用户级技能目录**（全局可用）；一个都没检测到时，装到通用位置 `~/.agents/skills/weifan/`。常用参数：`--en` 装英文版、`--list` 只看不动手、`--client=claude` 只装指定客户端、`--all` 全部候选都装。

也兼容社区 skills CLI：`npx skills add ban-boi/weifan-skill`（Vercel 的开放技能生态，同样一行命令）。

**手动安装**（任何支持 SKILL.md 通用技能标准的客户端）：把本目录复制到对应 skills 目录即可——

- **ZCode**：`~/.agents/skills/weifan/`（或 `~/.zcode/skills/`）
- **Claude Code**：`~/.claude/skills/weifan/`
- **Cursor / OpenClaw / DeepSeek harness**：按各自 skills 目录约定放入即可
- **英文用户**：用 `SKILL.en.md` 覆盖/替换为 `SKILL.md`（或一行安装时加 `--en`）

技能本体无依赖、无 API key，纯指令型，装完即用。

## 质量证据链

这个 skill 不是拍脑袋写的——它带着完整的开发-评测闭环（方法与数据见 [EVALUATION.md](EVALUATION.md)）：

- **39 场真实使用会话**语料（非合成场景）
- **12 场盲评复评**（评分代理不知分组）：术语准入违规场次 3/4 → 1/8；困惑信号轮占比 12.2% → 5.1%，满足信号 10.9% → 22.8%
- 措辞级**微测验证**：同一压测场景多副本跑，形态收敛才算措辞成立
- 迭代四版，每版改动先拿到失败证据（真实会话中的逐字引文）再动笔

## 模型要求

这是重纪律型 skill（约 150 行行为规则），**指令跟随能力强的模型效果最好**。弱模型常见退化：确认句退化为裸问"懂了吗"、术语漏定义、多问轮放弃归约——skill 内置了发送前静默关卡和长会话纪律重锚来对抗，但模型能力仍是下限的决定因素。

## 内容大于形式：按你的痛点裁剪

这份规则集的本质是**"真实痛点 → 对策"的映射**，不是必须整册供奉的教条。MIT 协议下它对你是完全开放的：

- **加**：你在用 AI 时踩到别的痛点，就照"痛点 → 一条可执行对策"的格式往 SKILL.md 里加一节；讲究一点的话，像本项目一样先拿到失败证据再定稿（方法见 [EVALUATION.md](EVALUATION.md)）
- **删**：哪条对策不合你的口味，直接删掉对应小节——喜欢比喻的可以整段删掉比喻纪律，大部分小节可独立增删，skill 其余部分照常工作
- **改**：措辞约束不住你的模型，就换成它听得进去的说法

抛砖引玉：重要的不是这 150 行的具体字句，而是"把 AI 问答改造成认知建模"这个方向。
